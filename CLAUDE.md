# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The Vite/React/TypeScript app lives in the `bicycle forum/` subdirectory (not the repo root) — run all commands from there:

```
cd "bicycle forum"
npm run dev       # start the Vite dev server
npm run build     # type-check (tsc -b) then production build
npm run lint      # eslint .
npm run preview   # preview the production build locally
```

There is no test runner configured yet (no test script, no test framework installed).

Supabase is set up: the client lives at `src/lib/supabaseClient.ts` (reads `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` from `.env.local` — copy `.env.example` to get started), generated row/table types are in `src/lib/database.types.ts`, and the schema lives in `supabase/migrations/01`–`30` (profiles/auth wiring, posts+comments, tags, badges, votes+reputation, hardening passes, an `avatars` Storage bucket, `posts.dislike_count`, `search_posts()`, comment replies, immutability guards on posts/comments' identity fields now that both are editable, a self-service `delete_own_account()` RPC, a `saved_posts` bookmarks table, a profile bio, and a `post-images` Storage bucket backing `posts.image_url`). Apply new migrations with the Supabase MCP tools (`apply_migration` against the project, then mirror the same SQL into a new numbered file here) rather than hand-editing the live schema; regenerate `database.types.ts` via `generate_typescript_types` after any schema change instead of hand-editing it. A migration that tightens a `check` constraint on a column already receiving writes (e.g. `29_bio_max_256.sql` lowering `profiles.bio`'s cap) should add it `not valid` and follow up with a separate `validate constraint`, so the `alter table` itself doesn't block on scanning/rejecting rows that are already out of the new, narrower bound - safe to skip only when the column genuinely has no real data yet to violate it, as was true there.

## Commit hygiene

Commit finished, working increments of the forum with clear, descriptive commit messages (not just at the end of a session) and push them, so `origin/main` always has a recent, working saved version of the project to fall back to. Verify `npm run lint` and `npm run build` pass before committing.

## Intended architecture (from Requirements.md)

The project is meant to be a **TypeScript + React + Vite** bicycle forum, with **Supabase** as the backing store and for authentication. Do not build a custom auth entity — Supabase auth is the system of record for login/session state.

Key domain entities and rules to preserve when implementing data models and validation:

- **User**: first name (4–32 chars) + optional last name (4–32 chars when given), email (valid, unique) and/or username. Username is set at registration and immutable afterward; an optional profile photo is stored in the `avatars` Storage bucket (public read, owner-only write) and referenced by `profiles.avatar_url`. An optional bio (`profiles.bio`, up to 256 chars - tightened from an initial 500 once it was actually in use) is shown on the user's public profile page.
- **Admin**: first name (4–32 chars) + optional last name (4–32 chars when given), email (valid, unique), optional phone number. Same `profiles` table and `last_name` constraint as User - there's no role-conditioned rule, so this follows User's last-name-is-optional change too.
- **Post**: belongs to a user, has a title (4–64 chars), content (16–8192 chars), an optional single uploaded image (`posts.image_url`, PNG/JPG/WEBP/GIF/AVIF, up to 5MB), comments, and separate upvote/downvote counts (`like_count`/`dislike_count`) — the UI shows their difference as a single score, with the raw split available on hover.
- **Comments** are replies to posts, authored by other users. Deleting a comment (its own author, or an admin) soft-deletes it - content becomes `[deleted]` rather than the row being removed, so the thread's structure (replies included) stays intact.
- **Votes**: one row per (voter, post-or-comment) in `votes` with `value` of `1` or `-1`; a trigger keeps `posts.like_count`/`dislike_count` and the content author's `profiles.reputation` in sync on insert/update/delete, and blocks voting on your own content.
- **Tags**: lowercase-only, deduplicated (reuse existing tag rows instead of creating duplicates), attached to a post at creation and editable afterward via the edit-post form. Post authors manage tags on their own posts (add and remove); admins can only remove tags from any post, never add one.
- **Reputation**: a per-user score that updates automatically when a post/comment is upvoted or downvoted (and reverses when a vote is removed).
- **Badges**: auto-awarded on milestones (post count, comment count, reputation thresholds, tenure); shown next to the username on posts and comments alike, and (with their earned date) on both the own-profile page and the public per-user profile page.

Application surfaces to keep separated by access level:

- **Public part** (no auth): landing page with platform stats (user count, post count), top 10 most-commented posts, 10 most recent posts, registration/login, light/dark mode toggle.
- **Private part** (authenticated users): browse/sort/filter posts, view a single post with comments/likes/actions inline, edit profile (username is immutable after registration; optional profile photo), create posts, edit/delete only own posts and comments, comment on any post.
- **Admin part** (admin role): search users by username/email/display name, block/unblock users (blocked users cannot post or comment), delete any post, view/filter/sort all posts.

Table organization in Supabase is left to the implementation, but should reflect the entities and relationships above (users, posts, comments, tags, post_tags, votes/reputation, badges).

- **Browse/search** (`/posts`, auth-guarded, `src/pages/PostsBrowse`): a navbar search bar (`src/components/SearchBar`) parses `#tag_name word word u/username` into tag filters, title words, and username lookups (an underscore in a `#tag` stands in for a space, since the box itself is space-delimited) via `parseSearchQuery()`/`src/lib/search.ts`, and navigates to `/posts?q=...`. A mode picker (`#search-bar-mode`, Posts/Tags/Users) to the search box's left auto-prepends the right prefix (nothing/`#`/`u/`) to every token typed, so using it means never having to type the prefixes by hand; its selection also swaps the input's placeholder. It's a hand-rolled button + absolutely-positioned menu, not a native `<select>` - a real `<select>`'s own popup can't be styled to match the pill (no cross-browser control over its background/corners), and its closed-state text centers differently from an `<input>` in Chrome vs. Firefox regardless of matching height/line-height/appearance:none, since the browser lays out a select's text internally rather than through plain CSS. The custom menu is deliberately sized `width: 100%` of the same `position: relative` trigger element it's anchored to, so it's always exactly as wide as - and horizontally centered with - the trigger, and shares the search bar's own background/border/radius tokens so it reads as a continuation of the pill rather than a separate control. On the results side, `describeSearchQuery()` reads the `q` string back into a mode (any `u/` token wins outright as a user search, since mixing users with post words/tags has no combined meaning; a pure `#tag` query with no plain words reads as a tags search; everything else - including a hand-typed mixed `#tag word` query - falls back to a plain posts search) and a display string with that mode's prefix stripped, driving both the results heading ("Results for"/"Tag results for"/"User results for") and, for a user-mode query, an entirely different results list: `searchUsers()` matches profiles whose username contains any given term (via `public_profiles()` with `.or()`/`.ilike()`, same batching RPC `getPublicProfiles` uses) and renders as avatar/username/reputation cards linking to `/users/:username`, bypassing `search_posts()` entirely. Both `searchUsers()` here and `searchAdminUsers()` in `src/lib/admin.ts` run their term through `escapeOrFilterValue()` (also in `src/lib/search.ts`) before splicing it into the `.or()` filter string - PostgREST treats `,`/`(`/`)` as structural in that syntax, so an unescaped literal one (e.g. searching a pasted "Smith, John") corrupts the filter and the query silently comes back empty rather than erroring loudly. Any new PostgREST `.or()` filter built from free-typed user input should route through the same helper. For posts/tags mode, the page lists matching posts (Most recent / Top score sort, Load more pagination) via the `search_posts()` Postgres function, which requires a post to match every given word and carry every given tag. Visiting `/posts` directly (e.g. the navbar's "Posts" link) is the same page with an empty query - all posts, most recent first.
- **`AuthProvider` loading-vs-profile gotcha**: `loading` (`src/auth/AuthProvider.tsx`) only tracks the initial `supabase.auth.getSession()` call - `profile` is fetched in a *separate* effect keyed off the resulting `userId`, so on a hard page load there's a real window where `loading` is already `false` and `session` is set, but `profile` is still `null` because its own fetch hasn't resolved yet. `RequireAuth` never notices, since it only checks `session`. This exact gap shipped as a bug in `RequireAdmin` first (only caught by testing a hard reload of an admin route, not a client-side nav to it, since the latter doesn't hit the gap - the profile fetch from the *previous* page's session has already long since resolved) - `AuthProvider` now also exposes a derived `profileLoading` (`!!userId && profileState?.userId !== userId`, computed alongside `profile` itself, not extra state - a naive `useState` set from inside the profile-fetch effect trips the `react-hooks/set-state-in-effect` lint rule) so a guard can tell "still fetching" apart from both "signed out" and "fetched, and it's genuinely null" (fetch failure, missing row) - the bare `if (!profile)` this project used at first only handled the first case and would otherwise hang on a blank page forever in the second. Any future guard that depends on `profile` should check `profileLoading` the same way `RequireAdmin` does, not infer it from `profile` being falsy.
- **Admin part** (`/admin/users`, `/admin/posts`, `src/pages/Admin`, guarded by `src/components/RequireAdmin` - no session → `/login`, signed in but `profile.role !== 'admin'` → `/` since there's no separate "unauthorized" page): the backend was already fully ready for this before any of it was built - `is_admin()`, the `"Owners and admins can view full profiles"`/`"Users and admins can update profiles"` policies on `profiles`, `"Authors and admins can delete posts"` on `posts`, and the admin branches of the `post_tags` insert/delete policies (all from earlier migrations) already covered every admin capability, so this needed no new migration, only new pages/routes calling existing or trivially-added library functions. `/admin` redirects to `/admin/users`; both pages share a small `Users | Posts` tab bar. **Users**: `src/lib/admin.ts`'s `searchAdminUsers()` queries `profiles` directly (not the public-safe `public_profiles()` view, since admins need `email`/`is_blocked`) with an explicit-submit search (username/email/first or last name, `ilike`, capped at 50 rows) - RLS alone is what makes this safe to query directly. Each result row has a Block (opens `ConfirmDialog`, danger-styled) or Unblock (applies immediately, no confirm, mirroring the app's existing asymmetric pattern for reversible actions like unsaving a post) button calling `setUserBlocked()`, surfacing a failure from either as an `.auth-form-error` line above the list; a row can't block itself (disabled, with a title tooltip) as a self-lockout safety rail, not a security boundary. **Posts**: a lighter, non-URL-synced version of `PostsBrowse`'s search/sort/Load-more flow (local state instead of `useSearchParams`, since this view isn't meant to be deep-linked) over the same `searchPosts()`/`parseSearchQuery()` from `src/lib/search.ts`; each row is a new `admin-post-row` (deliberately not `PostSummaryCard`, so its admin-only buttons can't leak into the regular card used elsewhere) with Delete (`ConfirmDialog`, reuses `deletePost()` from `src/lib/posts.ts`, removes the row from local state rather than re-querying) and "Remove tags" (a small custom modal in `AdminPosts.tsx`, not `ConfirmDialog` - it's a plain browse list rather than a confirm/cancel or save/cancel form, so it just reuses `ConfirmDialog.css`'s `.modal-overlay`/`.modal-card` classes directly) listing the post's tags as `.tag-bubble`s with only the existing remove (×) affordance - there's no add-a-tag input here, unlike `PostForm`'s own tag editor. Admins can only ever *remove* a tag from a post, never add one: `post_tags` INSERT is author-only as of migration `26_relax_lengths_soft_delete_comments_tags.sql`, so this can't reuse `replacePostTags()`'s clear-and-reinsert strategy (which would need INSERT to re-add every tag the admin didn't touch) - instead each × click calls a dedicated `removeTagFromPost()` (`src/lib/tags.ts`) that only issues a single targeted `post_tags` DELETE, taking effect immediately with no separate Save step (same "reversible action, no confirm needed" posture as Unblock above). Each post row also has a "Comments" button opening a similar browse modal listing that post's comments (reusing `getComments()`/`deleteComment()` from `src/lib/postDetail.ts`, the same ones `PostView` uses); deleting one opens a nested `ConfirmDialog` ("Delete comment") - both this and `PostView`'s own comment delete (see the note below) ended up moving off a native `window.confirm()` in this same session, since it blocks Claude in Chrome's browser automation and hung the tab on every comment-delete test; this admin one moved first (it had no other option, `window.confirm()` isn't a sensible fit for a delete button inside an already-open modal), and `PostView`'s own delete followed for the same testability reason plus consistency. Comment deletion is a soft delete (see the Comments entity note above) - `deleteComment()` now updates `content` to `DELETED_COMMENT_PLACEHOLDER` (`"[deleted]"`, exported from `postDetail.ts`) and sets `is_deleted` rather than issuing a DELETE, so both here and in `PostView` it's a local patch of the existing comment in state, not a refetch, and `posts.comment_count` is untouched (the row was never removed, so the "after delete" trigger that decrements it never fires). This needed a migration (`26_relax_lengths_soft_delete_comments_tags.sql`, following on from `25_admin_delete_comments.sql`'s earlier attempt at plain hard-delete-for-admins) - `comments.is_deleted` is new, and a `"Admins can update any comment"` UPDATE policy was added since the existing `"Non-blocked authors can update own comments"` policy only covers a user soft-deleting their own comment. A same-session code review then caught three more things the switch to soft-delete broke, fixed in a follow-up migration (`27_soft_delete_followups.sql`): migration 25's comments DELETE policy was never revoked, so a raw REST/console call could still hard-delete a comment (bypassing the soft-delete entirely) even though the app itself only ever issues the UPDATE now - dropped; a soft-deleted comment's `votes` rows used to get cascade-removed by a hard DELETE, which reversed the reputation they'd given the author via `handle_vote_change()` - a new `trg_comments_soft_delete_reverse_votes` trigger now deletes a comment's votes itself the moment `is_deleted` flips true, so that reversal still happens; and `check_and_award_badges()`'s comment-count badges (`first_comment`/`active_commenter`) counted every comment row regardless of `is_deleted`, so a soft-deleted comment kept counting toward them forever - the count now excludes `is_deleted` rows, matching what a hard delete used to do. `deleteComment()` (`src/lib/postDetail.ts`) also got stricter in the same pass: it's now async and selects the row back (`.select('id').maybeSingle()`) so an UPDATE that RLS silently matched zero rows - no `error`, just no `data`, indistinguishable from success otherwise - surfaces as a real error instead of the caller (`PostView`/`AdminPosts`) optimistically marking a comment deleted that the database never touched. `AdminPosts`' tag and comments browse modals (the plain `.modal-overlay`/`.modal-card` ones, not `ConfirmDialog`) also gained the same "backdrop click is a no-op mid-mutation" guard `ConfirmDialog` gets for free, keyed off `removingTag`/`deletingCommentId` - without it, clicking outside the modal while a tag removal or comment delete was still in flight closed the modal but left the request running unobserved. The navbar's "Admin" link (`src/components/Navbar`) only renders for `profile.role === 'admin'`, inside the same collapsible `<nav>` block as Posts/New post. Deliberately **not** built: no admin controls on `PostView`/`PostSummaryCard`/anywhere else in the regular app - every admin action lives only in this dedicated section (an explicit product call, so the feature's blast radius stays contained).

This needed a migration (`24_public_profiles_add_is_blocked.sql`) - `public_profiles()` (migration 09) exposed `role` already but not `is_blocked`, since until now nothing needed a blocked flag to be *publicly* visible (email/phone_number stay excluded, those are still genuinely private). A `RETURNS TABLE` function can't gain a column via `CREATE OR REPLACE`, only a full drop + recreate. `PublicProfile` (`src/lib/publicProfiles.ts`), `UserProfilePage` (`src/lib/userProfile.ts`), `getPublicProfiles()`, `searchUsers()` (`src/lib/search.ts`), and `getUserProfileByUsername()` all had to start threading `role`/`isBlocked` through alongside the fields they already carried.
- **`updated_at` gotcha**: `posts`/`comments` each have their own trigger (`set_posts_updated_at`/`set_comments_updated_at`) that only bumps `updated_at` when the user-editable columns actually change (title/content/image_url for posts, content for comments) - NOT the generic shared `set_updated_at()` used by `profiles`. If you add a new mutable column to either table, make sure it's covered by that same trigger's condition, or actions that touch it (like votes touching `like_count`) will start silently marking things as edited - this bit the post-images feature itself at first (see the Create/edit post note above): attaching an image via a follow-up `UPDATE` after a post's `INSERT` tripped this trigger and marked a brand-new post "(edited)", fixed by folding the image into the original insert instead.
- **`parent_comment_id` immutability gotcha**: `enforce_comment_parent_same_post()` blocks retargeting a reply to a *different* specific parent (or attaching one to a previously top-level comment), but deliberately allows it to become `null` - that's what the `ON DELETE SET NULL` cascade does when a comment's parent is deleted (orphaning the reply instead of destroying it), and that cascade fires through the same BEFORE UPDATE trigger. This no longer fires during normal use now that deleting a single comment is a soft delete (see the Comments entity note above) rather than an actual `DELETE` - a comment's row, and so its replies' `parent_comment_id`, only really goes away via the `posts`→`comments` cascade when the whole post is deleted, which removes the entire tree together and so never needs to orphan anything. The trigger (and this guard) still exist as a safety net for that path and for any future direct hard-delete - if you tighten this guard again, keep the null case working.
- **Button chrome gotcha**: the shared `.button`/`.button.primary`/`.button.danger` classes live in `src/pages/Home/Home.css` (not ideal, but that's where they've always been, and every page's CSS bundles into one global stylesheet regardless of which component imports it, since nothing here is code-split). A plain `<button className="button">` (no `.primary`/`.danger`) needs the `button.button` background rule there too: `:root` sets `color-scheme: light dark`, so an unstyled native `<button>` gets the browser's own dark or light chrome based on the OS preference, not this app's manual theme toggle - the two can disagree (e.g. OS dark + app toggled to light) and produce unreadable text. `<a className="button">` doesn't need this since anchors don't get that native chrome.
- **Shared bits**: `PasswordInput` (`src/components/PasswordInput`) gives every password field a show/hide eye-icon toggle. `formatDateTime()` (`src/lib/formatDate.ts`) renders timestamps in the viewer's own timezone, year down to minutes. `src/lib/publicProfiles.ts` has the shared `public_profiles()` batching helper used by posts/postDetail/search. The page always reserves a vertical scrollbar (`overflow-y: scroll` on `:root`) so short pages don't shift width relative to long ones.
