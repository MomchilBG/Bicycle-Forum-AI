# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The Vite/React/TypeScript app lives in the `bicycle forum/` subdirectory (not the repo root) — run all commands from there:

```
cd "bicycle forum"
npm run dev       # start the Vite dev server
npm run build     # type-check (tsc -b) then production build
npm run lint      # eslint .
npm run preview   # preview the production build locally
```

There is no test runner configured yet (no test script, no test framework installed).

Supabase is set up: the client lives at `src/lib/supabaseClient.ts` (reads `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` from `.env.local` — copy `.env.example` to get started), generated row/table types are in `src/lib/database.types.ts`, and the schema lives in `supabase/migrations/01`–`23` (profiles/auth wiring, posts+comments, tags, badges, votes+reputation, hardening passes, an `avatars` Storage bucket, `posts.dislike_count`, `search_posts()`, comment replies, immutability guards on posts/comments' identity fields now that both are editable, a self-service `delete_own_account()` RPC, and a `saved_posts` bookmarks table). Apply new migrations with the Supabase MCP tools (`apply_migration` against the project, then mirror the same SQL into a new numbered file here) rather than hand-editing the live schema; regenerate `database.types.ts` via `generate_typescript_types` after any schema change instead of hand-editing it.

## Commit hygiene

Commit finished, working increments of the forum with clear, descriptive commit messages (not just at the end of a session) and push them, so `origin/main` always has a recent, working saved version of the project to fall back to. Verify `npm run lint` and `npm run build` pass before committing.

## Intended architecture (from Requirements.md)

The project is meant to be a **TypeScript + React + Vite** bicycle forum, with **Supabase** as the backing store and for authentication. Do not build a custom auth entity — Supabase auth is the system of record for login/session state.

Key domain entities and rules to preserve when implementing data models and validation:

- **User**: first name + last name (4–32 chars each), email (valid, unique) and/or username. Username is set at registration and immutable afterward; an optional profile photo is stored in the `avatars` Storage bucket (public read, owner-only write) and referenced by `profiles.avatar_url`.
- **Admin**: first name + last name (4–32 chars each), email (valid, unique), optional phone number.
- **Post**: belongs to a user, has a title (16–64 chars), content (32–8192 chars), comments, and separate upvote/downvote counts (`like_count`/`dislike_count`) — the UI shows their difference as a single score, with the raw split available on hover.
- **Comments** are replies to posts, authored by other users.
- **Votes**: one row per (voter, post-or-comment) in `votes` with `value` of `1` or `-1`; a trigger keeps `posts.like_count`/`dislike_count` and the content author's `profiles.reputation` in sync on insert/update/delete, and blocks voting on your own content.
- **Tags**: lowercase-only, deduplicated (reuse existing tag rows instead of creating duplicates), attached to a post at creation and editable afterward via the edit-post form. Post authors manage tags on their own posts; admins can manage tags on any post (not yet built - see status below). Tags drive search and are clickable wherever shown.
- **Reputation**: a per-user score that updates automatically when a post/comment is upvoted or downvoted (and reverses when a vote is removed).
- **Badges**: auto-awarded on milestones (post count, comment count, reputation thresholds, tenure); shown next to the username on posts and comments alike, and (with their earned date) on both the own-profile page and the public per-user profile page.

Application surfaces to keep separated by access level:

- **Public part** (no auth): landing page with platform stats (user count, post count), top 10 most-commented posts, 10 most recent posts, registration/login, light/dark mode toggle.
- **Private part** (authenticated users): browse/sort/filter posts, view a single post with comments/likes/actions inline, edit profile (username is immutable after registration; optional profile photo), create posts, edit/delete only own posts and comments, comment on any post.
- **Admin part** (admin role): search users by username/email/display name, block/unblock users (blocked users cannot post or comment), delete any post, view/filter/sort all posts.

Table organization in Supabase is left to the implementation, but should reflect the entities and relationships above (users, posts, comments, tags, post_tags, votes/reputation, badges).

## Current implementation status

What's built so far, so a new session doesn't have to rediscover it from the diff:

- **Auth**: `src/auth/AuthProvider.tsx` + `AuthContext.ts` wrap Supabase auth, exposing `session`, `user`, `profile` (the `profiles` row), `loading`, `signOut`, and `refreshProfile` (call after writing to `profiles` so the rest of the app picks up the change without a reload). Register/Login pages are built (`src/pages/Register`, `src/pages/Login`); login accepts a username or email, resolving a username to its email via the `email_for_username` RPC first. Route guarding for authenticated-only pages is `src/components/RequireAuth/RequireAuth.tsx`.
- **Public part**: Home page (`src/pages/Home`) has the hero, platform stats (from the `platform_stats()` SECURITY DEFINER function - not a plain view; a `security_invoker` view here undercounted `user_count` since profiles RLS only lets a non-admin see their own row, same class of bug `public_profiles()` was already written to avoid), and the most-commented/most-recent lists (10 each, via `src/lib/posts.ts`). The Join/Log in CTAs hide once signed in. Light/dark theme toggle is in `src/theme/`.
- **Navbar** (`src/components/Navbar`): Home, a "Posts" link (signed-in users only, to `/posts` with no query - just the plain browse view), "New post" (signed-in, non-blocked users), a search bar (signed-in only), then the signed-in user's avatar (linking to `/users/:username` - the same public profile page a username click anywhere else goes to, which shows an "Edit your profile" link for the viewer's own profile) and the theme toggle. There's no separate log-out control here — it's a bottom "danger zone" row on the profile edit page instead (see below), to avoid accidental clicks. It's `position: sticky` (stays visible while scrolling a long thread) - if you touch `#root`'s overflow again, keep it `overflow-x: clip` rather than `hidden`, since `hidden` implicitly forces `overflow-y: auto` and silently breaks the sticky positioning. Below 640px, the brand link and `<nav>` (Home/Posts/New post, or Home/Log in/Register signed out) collapse behind a hamburger `#nav-menu-toggle` button so the row keeps the search bar, avatar, and theme toggle inline; `#nav-menu` wraps both and is `display: contents` above that breakpoint (so it's transparent to desktop's flex layout) and an absolutely-positioned dropdown panel (`.open`) below it. Every link inside closes the menu via an `onClick`. The search bar's own ≤1024px "drop to full width on its own row" rule (`SearchBar.css`) is overridden again at ≤640px back to inline, since the hamburger already frees up the row.
- **Profile edit page** (`/profile`, auth-guarded, `src/pages/Profile`): deliberately editing-only now (an explicit product call) - it does **not** show stats, badges, or a posts list; those live only on the public per-user profile page below. Laid out as a stack of boxed panels (`.profile-box`, `src/pages/profileShared.css`): a "Profile photo" box (avatar preview + "Select image"/"Apply" buttons - picking a file just stages it and shows its name, "Apply" stays disabled until a file is staged, and only then does it upload via `src/lib/profile.ts` and clear the staged file), a two-up `.profile-grid-2` row of read-only "Username"/"Email" boxes, another `.profile-grid-2` row with the "Your name" and "Change password" forms, and a bottom `#profile-danger-zone` row with "Log out" and a red "Delete profile" button. Deleting the account opens the shared `ConfirmDialog` (below) with a password field: it re-authenticates via `supabase.auth.signInWithPassword()` first (so the plaintext password never reaches the database, only Supabase Auth's own check does), then calls the `delete_own_account()` RPC (migration `22_delete_own_account.sql`, `SECURITY DEFINER`, `authenticated`-only - watch out, Supabase grants `EXECUTE` to `anon`/`authenticated` by default on new public-schema functions, so a plain `revoke ... from public` isn't enough, you need an explicit `revoke ... from anon` too), which deletes the `auth.users` row and lets `on delete cascade` take out the profile and everything under it (posts/comments/badges/votes).
- **`ConfirmDialog`** (`src/components/ConfirmDialog`): a small reusable modal (title/message/children slot for extra fields/Cancel+Confirm buttons, optional `danger` styling, `confirming`/`confirmDisabled`/`error` props) used for the account-delete and post-delete confirmations below - backdrop click is a no-op while `confirming` is true, so an in-flight request can't be dismissed out from under its own error message. Comment deletion still uses a native `window.confirm()` (see the post view note below).
- **Create/edit post** (`/posts/new` and `/posts/:id/edit`, both auth-guarded, the latter also checking the viewer owns the post): share `src/components/PostForm` (title/content/tags field - type + "Add tag" button or Enter, lowercased like the username field, shown as removable bubbles) - `src/pages/CreatePost` and `src/pages/EditPost` differ only in initial values and the submit handler (insert vs. update-and-diff-tags), and creating a post navigates straight to the new post's page (not the profile page - that was a bug). `PostForm`'s optional `cancelHref` prop renders a Cancel button next to the submit button (both `flex: 1` in `#post-form-actions`, so one alone still fills the width); only `EditPost` passes it, pointing back at `/posts/:id` - `CreatePost` has no equivalent "discard" affordance. Blocked users see a notice instead of the form (also enforced server-side by RLS). `src/lib/tags.ts` reuses an existing `tags` row by name instead of creating a duplicate; `replacePostTags()` handles the edit case by clearing and reattaching rather than diffing.
- **Post view** (`/posts/:id`, `src/pages/PostView`, deliberately **not** auth-guarded — anyone can read a post and its comments, unlike the "Private part" grouping above, per an explicit product call): author card (avatar level with name/username, badges in their own row underneath), title/content, clickable tags (link to the equivalent search) under the content, then a `#post-vote-actions` row with the upvote/downvote arrows plus a Save/Saved bookmark button (any signed-in user, own post included; backed by the `saved_posts` table via `src/lib/savedPosts.ts` and `PostDetail.isSaved`; filled/primary-styled when saved) all on the left, and, on the right, Edit/Delete buttons for the post's own author, separated from the comments section below by a bottom border on that row. Save and Edit/Delete render as real `.button`s now (not the plain-text `.action-link` style comments still use) so they read as more prominent, deliberate actions. A blocked user can still remove an existing bookmark but can't create a new one (mirrors how vote removal, unlike casting a vote, was never gated on `is_blocked()` - see `saved_posts`' RLS policies). Both post and comments show "(edited)" next to their timestamp once their content has actually changed (not just voted on - see the `updated_at` note below). The comments section starts with the "Comments (N)" heading immediately followed by the comment composer (so leaving a comment doesn't need scrolling past the whole thread), then the comment list. Each comment shows its author's badges next to their username, can be replied to (one level of nesting - `comments.parent_comment_id`; replies don't themselves offer a further "Reply"), and its own author gets Edit (inline) / Delete links. Voting, commenting, replying, editing and deleting all require a signed-in, non-blocked user, enforced both client-side and via RLS/triggers (`src/lib/postDetail.ts` has the queries/mutations); signed-out visitors see "Log in to vote"/"Log in to comment" prompts instead. Deleting the post opens the shared `ConfirmDialog` and, on success, navigates to the author's own public profile page (not `/profile`, which no longer lists posts). Deleting a *comment* still uses a native `window.confirm()` - fine for real users, but it blocks Claude in Chrome's browser automation (per the tool's own warning), so verify comment delete via a direct authenticated REST call instead of clicking it when testing.
- **Public per-user profile page** (`/users/:username`, `src/pages/UserProfile`, not auth-guarded — same public-read call as post view): avatar, names, username, and "Joined {date}" (date-only via `formatDate()`, not the timestamped `formatDateTime()` badges/posts use - it sits on the same line as the names, where reputation used to be before it moved into Stats), plus a `.profile-grid-2` row with the "Stats" box and the earned-badges box side by side (Stats alone, full-width, when there are no badges yet), and that user's posts (reused `getPostsByAuthor`/`PostSummaryCard`). Stats is a two-column vertical list (`.profile-stats-columns`, split by `Math.ceil(items.length / 2)`) of label/value rows in this order: Reputation, Posts, (Saved, own profile only), Comments made, Comments earned (comments received across that user's own posts - just `sum(postSummary.commentCount)`, no extra query since the posts list is already fetched). **Only when viewing your own profile**, the Posts box also gets a Posts/Saved tab pair (`#user-profile-posts-tabs`) above the list, and its heading reads "Created posts" (vs. "Saved posts") depending on which tab is active - reusing the same box and `PostSummaryCard` list to show `getSavedPostsByUser()` results instead. The saved list is fetched lazily on first click and cached in state, but the Saved *count* (shown in Stats regardless of which tab is open) is fetched eagerly since Stats needs it up front. Looked up via `src/lib/userProfile.ts`'s `getUserProfileByUsername()`, which resolves the username through the `public_profiles()` RPC (case-insensitively) rather than exposing `profiles` directly. If the viewer is looking at their own username here, an "Edit your profile" link to `/profile` appears instead of duplicating the edit form. Usernames are clickable through to this page wherever they appear: post author card and comment authors in PostView, and the "by {username}" byline in `PostSummaryCard` (used on Home, Profile, PostsBrowse, and this page itself).
- **Browse/search** (`/posts`, auth-guarded, `src/pages/PostsBrowse`): a navbar search bar (`src/components/SearchBar`) parses `#tag_name word word u/username` into tag filters, title words, and username lookups (an underscore in a `#tag` stands in for a space, since the box itself is space-delimited) via `parseSearchQuery()`/`src/lib/search.ts`, and navigates to `/posts?q=...`. A mode picker (`#search-bar-mode`, Posts/Tags/Users) to the search box's left auto-prepends the right prefix (nothing/`#`/`u/`) to every token typed, so using it means never having to type the prefixes by hand; its selection also swaps the input's placeholder. It's a hand-rolled button + absolutely-positioned menu, not a native `<select>` - a real `<select>`'s own popup can't be styled to match the pill (no cross-browser control over its background/corners), and its closed-state text centers differently from an `<input>` in Chrome vs. Firefox regardless of matching height/line-height/appearance:none, since the browser lays out a select's text internally rather than through plain CSS. The custom menu is deliberately sized `width: 100%` of the same `position: relative` trigger element it's anchored to, so it's always exactly as wide as - and horizontally centered with - the trigger, and shares the search bar's own background/border/radius tokens so it reads as a continuation of the pill rather than a separate control. On the results side, `describeSearchQuery()` reads the `q` string back into a mode (any `u/` token wins outright as a user search, since mixing users with post words/tags has no combined meaning; a pure `#tag` query with no plain words reads as a tags search; everything else - including a hand-typed mixed `#tag word` query - falls back to a plain posts search) and a display string with that mode's prefix stripped, driving both the results heading ("Results for"/"Tag results for"/"User results for") and, for a user-mode query, an entirely different results list: `searchUsers()` matches profiles whose username contains any given term (via `public_profiles()` with `.or()`/`.ilike()`, same batching RPC `getPublicProfiles` uses) and renders as avatar/username/reputation cards linking to `/users/:username`, bypassing `search_posts()` entirely. For posts/tags mode, the page lists matching posts (Most recent / Top score sort, Load more pagination) via the `search_posts()` Postgres function, which requires a post to match every given word and carry every given tag. Visiting `/posts` directly (e.g. the navbar's "Posts" link) is the same page with an empty query - all posts, most recent first.
- **`AuthProvider` loading-vs-profile gotcha**: `loading` (`src/auth/AuthProvider.tsx`) only tracks the initial `supabase.auth.getSession()` call - `profile` is fetched in a *separate* effect keyed off the resulting `userId`, so on a hard page load there's a real window where `loading` is already `false` and `session` is set, but `profile` is still `null` because its own fetch hasn't resolved yet. `RequireAuth` never notices, since it only checks `session`. Any future guard that also needs `profile` (like `RequireAdmin` below) must explicitly wait out that gap - `if (!profile) return null` alongside the `loading` check - or it'll misread "still loading" as "logged in but doesn't qualify" and redirect somewhere wrong; this exact bug shipped and was only caught by testing a hard reload of an admin route, not a client-side nav to it (which doesn't hit the gap, since the profile fetch from the *previous* page's session has already long since resolved).
- **Admin part** (`/admin/users`, `/admin/posts`, `src/pages/Admin`, guarded by `src/components/RequireAdmin` - no session → `/login`, signed in but `profile.role !== 'admin'` → `/` since there's no separate "unauthorized" page): the backend was already fully ready for this before any of it was built - `is_admin()`, the `"Owners and admins can view full profiles"`/`"Users and admins can update profiles"` policies on `profiles`, `"Authors and admins can delete posts"` on `posts`, and the admin branches of the `post_tags` insert/delete policies (all from earlier migrations) already covered every admin capability, so this needed no new migration, only new pages/routes calling existing or trivially-added library functions. `/admin` redirects to `/admin/users`; both pages share a small `Users | Posts` tab bar. **Users**: `src/lib/admin.ts`'s `searchAdminUsers()` queries `profiles` directly (not the public-safe `public_profiles()` view, since admins need `email`/`is_blocked`) with an explicit-submit search (username/email/first or last name, `ilike`, capped at 50 rows) - RLS alone is what makes this safe to query directly. Each result row has a Block (opens `ConfirmDialog`, danger-styled) or Unblock (applies immediately, no confirm, mirroring the app's existing asymmetric pattern for reversible actions like unsaving a post) button calling `setUserBlocked()`; a row can't block itself (disabled, with a title tooltip) as a self-lockout safety rail, not a security boundary. **Posts**: a lighter, non-URL-synced version of `PostsBrowse`'s search/sort/Load-more flow (local state instead of `useSearchParams`, since this view isn't meant to be deep-linked) over the same `searchPosts()`/`parseSearchQuery()` from `src/lib/search.ts`; each row is a new `admin-post-row` (deliberately not `PostSummaryCard`, so its admin-only buttons can't leak into the regular card used elsewhere) with Delete (`ConfirmDialog`, reuses `deletePost()` from `src/lib/posts.ts`, removes the row from local state rather than re-querying) and "Manage tags" (`ConfirmDialog` repurposed as a modal, `getTagsForPost()`/`replacePostTags()` from `src/lib/tags.ts` - both already worked for any post regardless of author, since they only ever touch `post_tags`/`tags`, never the author-gated `posts` row itself; the modal's tag-bubble editor duplicates `PostForm`'s small add/remove interaction rather than extracting it, and reuses its `#tag-input-row`/`#tag-bubble-list`/`.tag-bubble` classes since this app has one global CSS bundle regardless of which component imports what - see the button-chrome gotcha below for the same reasoning). The navbar's "Admin" link (`src/components/Navbar`) only renders for `profile.role === 'admin'`, inside the same collapsible `<nav>` block as Home/Posts/New post. Deliberately **not** built: no admin controls on `PostView`/`PostSummaryCard`/anywhere else in the regular app - every admin action lives only in this dedicated section (an explicit product call, so the feature's blast radius stays contained).
- **404**: any unmatched path renders `src/pages/NotFound` inside the normal layout (navbar still shows).
- **Colors**: badges are gold/amber (`--badge`/`--badge-bg`/`--badge-border`) and tags are purple/accent (`--accent`/`--accent-bg`/`--accent-border`) - deliberately different so the two pill styles read as distinct concepts. Error messages (`.auth-error`, `.auth-form-error`) are tinted bubbles via `--danger-bg`/`--danger-border`, sized to their text.
- **`updated_at` gotcha**: `posts`/`comments` each have their own trigger (`set_posts_updated_at`/`set_comments_updated_at`) that only bumps `updated_at` when the user-editable columns actually change (title/content for posts, content for comments) - NOT the generic shared `set_updated_at()` used by `profiles`. If you add a new mutable column to either table, make sure it's covered by that same trigger's condition, or actions that touch it (like votes touching `like_count`) will start silently marking things as edited.
- **`parent_comment_id` immutability gotcha**: `enforce_comment_parent_same_post()` blocks retargeting a reply to a *different* specific parent (or attaching one to a previously top-level comment), but deliberately allows it to become `null` - that's what the `ON DELETE SET NULL` cascade does when a comment's parent is deleted (orphaning the reply instead of destroying it), and that cascade fires through the same BEFORE UPDATE trigger. An earlier, stricter version of this trigger blocked that too, which made deleting any commented-on comment fail outright - if you tighten this guard again, keep the null case working and verify a parent-with-replies can still be deleted.
- **Button chrome gotcha**: the shared `.button`/`.button.primary`/`.button.danger` classes live in `src/pages/Home/Home.css` (not ideal, but that's where they've always been, and every page's CSS bundles into one global stylesheet regardless of which component imports it, since nothing here is code-split). A plain `<button className="button">` (no `.primary`/`.danger`) needs the `button.button` background rule there too: `:root` sets `color-scheme: light dark`, so an unstyled native `<button>` gets the browser's own dark or light chrome based on the OS preference, not this app's manual theme toggle - the two can disagree (e.g. OS dark + app toggled to light) and produce unreadable text. `<a className="button">` doesn't need this since anchors don't get that native chrome.
- **Shared bits**: `PasswordInput` (`src/components/PasswordInput`) gives every password field a show/hide eye-icon toggle. `formatDateTime()` (`src/lib/formatDate.ts`) renders timestamps in the viewer's own timezone, year down to minutes. `src/lib/publicProfiles.ts` has the shared `public_profiles()` batching helper used by posts/postDetail/search. The page always reserves a vertical scrollbar (`overflow-y: scroll` on `:root`) so short pages don't shift width relative to long ones.
